# M0 실행 계획과 검증표

기준일: 2026-09-30. 상위 문서는 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)이며 요구사항·시험 ID는 제공된 통합 명세 v0.1을 따른다. 이 문서는 작업 범위와 판정 기준을 정하며, 구현과 실제 실행 상태는 [STATUS.md](STATUS.md)를 따른다.

`T00-01~04`는 원본 작업 ID다. `T00-04.1~4`는 이번 계획에서 나눈 하위 작업이며, `BASE-00`은 착수 준비를 추적하기 위한 추가 ID다. 이 문서는 M0 범위의 검증표이며 전체 P0/P0B 대응표는 BASE-00에서 작성한다.

## 작업 순서와 의존성

| 작업 | 선행 조건 | 산출물 | M0에서 확인할 범위 |
|---|---|---|---|
| BASE-00 | 없음 | 저장소 기준선·환경표·요구/시험 대응표·음원 manifest | 빌드 착수 조건, 실기기/모델/음원 준비 상태 |
| T00-01 | BASE-00의 문서·빌드 환경 준비 | Avalonia 앱·Rust worker·최소 IPC·check 스크립트 | 실제 프로세스 통신과 수명 |
| T00-02 | Windows의 T00-01 | Windows capture probe | WASAPI PCM·장치 변경 |
| T00-03 | Mac 환경과 해당 OS의 T00-01 | macOS bridge·최소 앱 번들 | ScreenCaptureKit PCM·권한·수명 |
| T00-04.1 | BASE-00의 모델/음원 준비 | 실제 ASR·번역 비교 harness | 품질·처리시간·메모리 초기 기준선 |
| T00-04.2 | T00-01, T00-04.1의 ASR 실행 경로 | native 추론 취소·재시작 probe | 모델 수명과 재개 지연 |
| T00-04.3 | 해당 OS의 T00-01 | 최소 자막 창 probe | topmost·투명도·포커스·Spaces |
| T00-04.4 | T00-04.1 | ASR/번역 동시 부하 보고 | 자원 경쟁과 후보 유지 여부 |

BASE-00의 모델/음원 미확보는 T00-01을 막지 않는다. T00-02와 T00-03은 서로 독립적이며, 파일 음원을 사용하는 T00-04.1도 캡처 구현 완료를 기다릴 필요가 없다. Mac 접근이 불가능하면 Mac 결과는 BLOCKED로 남기고 Windows·프로토콜·fixture 작업을 진행한다. M0 전체 통과에는 두 OS의 실제 결과가 필요하다.

## BASE-00: 착수 준비

- 기존 `AGENTS.md`와 계획을 보존하며 통합 명세의 개념·요구·아키텍처·계약·검증·로드맵을 저장소 문서로 옮긴다. 원본의 문서 경계와 요구 ID를 유지한다.
- Git 초기화 여부를 확인하고 변경 추적, 산출물 제외 규칙, `docs/STATUS.md`, `docs/REQUIREMENTS_MATRIX.md`, `docs/DECISIONS.md`를 마련한다. 대응표에는 요구 ID, 구현 작업, 수용 시험, 대상 OS, 결과 경로와 미실행 사유를 둔다.
- Windows/Mac의 실제 접근 방법과 OS·CPU/GPU·RAM을 기록한다. Rust/.NET SDK, C/C++ 빌드 도구, CMake, Mac의 Xcode/Swift 등 필요한 도구를 확인한다. 여기서는 사용 가능한 버전과 미확인 조합을 기록한다. UI/worker 버전은 T00-01의 실제 빌드로, native 구성요소는 해당 캡처/모델 probe에서 호환성을 확인해 고정한다.
- 모델 시험용 음원에는 출처·사용 범위·해시·정답 전사·발화 구간을 둔다. 초기 묶음은 언어별 2~8초 발화 최소 10개, 긴 발화와 실제 반복, 무음/배경음 사례를 포함한다. 이 수량은 이번 계획의 소규모 실험 기준이며 출시 품질 표본으로 사용하지 않는다.
- **완료 조건:** T00-01의 입력 문서와 첫 빌드 환경이 준비되고, 모델/음원/Mac 미확보 항목에는 영향받는 작업과 확보 방법이 있다. 모델 다운로드는 구체적인 파일·크기·라이선스를 확인하고 사용자 동의를 받은 후 수행한다.
- **요구:** NF-008. 모델 manifest는 MOD-001/002의 검증 입력이며 설치 기능 구현은 M4다.

## T00-01: UI와 worker 최소 IPC

- **구현:** `apps/EchoSub.Desktop/`, 필요한 최소 Rust crates, `schemas/`, `scripts/check.ps1`·`scripts/check.sh`. `hello`, `ping`, `get_state`, `shutdown`과 구조화 오류를 구현한다. 미구현 명령은 `UNSUPPORTED_CAPABILITY`로 응답한다.
- **계약:** UTF-8 NDJSON, 프로토콜 major version, request ID, 메시지 최대 256 KiB. 초기 네 명령의 schema/DTO를 함께 고정하고 나머지는 해당 기능 작업에서 추가한다.
- **검증:** UI가 실제 worker를 실행하고 네 명령을 교환한다. 잘못된 version/JSON/대형 메시지를 거부한다. 한국어·일본어·emoji·escaped newline이 왕복한다. stdout에는 프로토콜만 있으며 stderr도 비동기로 소비한다.
- **수명:** 정상 종료, worker 강제 종료, 부모 EOF, 느린 reader에서 무한 대기·고아 프로세스가 없는지 확인한다. shutdown은 원본의 최대 5초 대기 후 소유 프로세스 종료 정책을 따른다. 오류 후 자동 재캡처는 하지 않는다.
- **완료 조건:** 현재 OS의 빌드와 위 시험이 통과하고, mock 표시와 capability가 실제 상태를 나타낸다. 다른 OS 결과는 별도 기록하며 해당 OS의 캡처 probe 전에 검증한다.
- **실패 시:** 프로토콜·프로세스 수명을 먼저 수정한다. 이 경로에 의존하는 캡처 UI 통합은 보류한다.
- **요구/시험:** OPS-001, NF-008 / IT-001, IT-002, UT-009의 IPC 범위.

## T00-02: Windows 실제 시스템 오디오

- **구현:** WASAPI loopback capture probe와 포맷·타임스탬프·레벨·drop 진단. 재생 음원은 준비된 fixture를 사용하고 캡처 원본을 기본 저장하지 않는다.
- **검증:** 마이크 없이 시스템 재생 음원으로 10분 PCM을 수신한다. 실제 sample rate/channel layout, silent/discontinuity, packet 중단을 기록한다. 기본 장치 추종 전환과 고정 장치 분리를 각각 수행한다.
- **완료 조건:** 재생/무음 구간과 PCM 레벨이 대응한다. 장치 변경·분리에서 hang/crash가 없고, 불연속을 식별한다. 고정 장치 분리는 명시적 중단/복구 상태로 끝나며 임의 장치로 전환하지 않는다.
- **실패 시:** 포맷·콜백·장치 수명을 분리해 수정한다. 소리가 수신되지 않는 원인을 ASR 문제로 넘기지 않는다.
- **요구/시험:** AUD-001/002/005, NF-001 / HW-W01, HW-W02. 최종 세션 시간축은 M1에서 검증한다.

## T00-03: macOS 캡처와 앱 번들 권한

- **구현:** ScreenCaptureKit bridge, worker의 run loop와 콜백 수명, UI/worker/bridge를 담은 최소 `.app`.
- **검증:** 실제 `.app` 실행으로 시스템 오디오 10분 수신, 권한 거부→안내→허용→재시도, 앱 재실행을 확인한다. 사용한 서명 방식·bundle identity·권한 귀속 프로세스를 기록한다. stop 완료 후 callback이 끝난 다음 버퍼/handle을 해제한다.
- **완료 조건:** 선택한 번들 구조에서 실제 PCM과 권한 복구가 동작하고 종료 후 callback 접근·고아 worker가 없다. 개발용 서명 결과를 배포 서명·공증 통과로 확대하지 않는다.
- **실패 시:** 권한 귀속·번들·bridge 경계를 먼저 재검토한다. 대체 캡처 API 검토는 실패 증거를 남긴 뒤 결정한다. Mac 미확보는 BLOCKED다.
- **요구/시험:** AUD-001/003/004/005, OPS-001/002 / HW-M01, HW-M02의 개발 번들 범위. 최종 OPS-002 판정은 M5다.

## T00-04.1: 실제 모델의 초기 기준선

- **구현:** 고정된 whisper.cpp commit/binding의 재사용 가능한 모델 context와 작은 fixture harness. 다국어 `base`/`small`을 같은 음원으로 비교하고, 번역 후보 하나를 실제 로컬 서버로 호출한다. Windows/Mac의 실제 backend와 모델 변환본을 각각 기록한다.
- **측정:** 영어 WER, 일본어·한국어 CER와 원문 차이, 번역 방향별 최소 10문장의 의미·숫자·부정·추가 내용, 모델 load/warm-up 시간, decode 시간, 메모리. 실제 가속 경로와 CPU 경로를 구분한다.
- **완료 조건:** 양 OS에서 재현 가능한 모델 실행과 비교 결과가 있고, 후보별 채택·수정·보류 이유가 기록돼 있다. 짧은 표본에서 발견한 중대 오류에는 M3 재검증 항목을 연결한다. 처리시간은 UI까지의 자막 지연으로 보고하지 않는다.
- **실패 시:** 모델·binding·backend·입력 자료 중 원인을 분리한다. 실행이나 품질에 해결 가능한 경로가 없으면 후보 채택을 보류한다.
- **요구/시험:** ASR-001, TR-001/002, MOD-001, NF-008 / 추가 probe `P0-MODEL`. M2의 시스템 전사 및 M3 품질 수용 시험을 대신하지 않는다.

## T00-04.2: 실제 추론 중 취소·재시작

- **구현:** 실제 decode 도중 취소·즉시 재시작·종료를 요청하는 probe. PCM과 context의 소유 스레드·해제 순서를 기록한다.
- **검증:** 각 채택 backend에서 동작 중임이 확인된 decode를 대상으로 최소 10회 반복한다. 취소 요청→decode 반환→다음 작업 시작, 정상/강제 종료를 각각 측정한다. warm-up/CPU fallback은 결과에 표시한다.
- **완료 조건:** 같은 context에 decode가 겹치거나 실행 중 context가 해제되지 않는다. 종료 후 새 decode가 가능하고, 측정 결과에 따라 협력 취소·완료 대기·worker 재시작 중 사용할 정책이 정해져 있다. 지원하지 않는 취소를 성공으로 간주하지 않는다.
- **실패 시:** 수명 오류는 수정 전 채택을 보류한다. 긴 취소 지연은 스케줄러 입력 조건으로 남긴다. 모델 반환 시간과 캡처 Stop 500ms 목표를 혼동하지 않는다.
- **요구/시험:** NF-003/004, OPS-001 / 추가 probe `P0-CANCEL`. epoch 결과 폐기는 M1/M2에서 별도로 검증한다.

## T00-04.3: 기본 오버레이

- **구현:** mock 자막임을 표시한 최소 topmost/투명 배경 창. 실제 전사와 독립적으로 실행한다.
- **검증:** 양 OS의 일반/테두리 없는 창 위 표시, 다른 앱 입력 포커스 유지, 위치·크기 조절을 확인한다. Mac은 Spaces 전환도 기록한다. 사용한 OS·모니터·대상 앱 조합을 남긴다.
- **완료 조건:** 기본 수용 범위에서 접근 가능한 자막 창이 동작하며 지원되지 않는 조합이 식별돼 있다. 클릭 통과·잠금 해제·전체 다중 화면 검증은 M3/M4에 배정한다.
- **실패 시:** 플랫폼 창 어댑터를 보완한다. 필요한 조합이 불가능하면 UX/지원 범위 결정을 남긴다.
- **요구/시험:** UI-002/004 / HW-UI01의 기본 창 범위. UI-003 전체 통과로 기록하지 않는다.

## T00-04.4: ASR와 번역 동시 부하

- **선행:** T00-04.1에서 실행 가능성이 확인된 후보, 실제 두 기준 장치 또는 대체 장치임을 명시한 환경.
- **검증:** 고정 fixture를 ASR 단독, 번역 단독, 동시 실행으로 각각 최소 5분 반복한다. 처리시간 분포·메모리·실행 완료 수·대기 증가를 비교한다. 게임 없는 동일 설정을 사용하고 실패/OOM도 결과에 포함한다. 시험 시간은 이번 계획의 초기 probe 기준이다.
- **완료 조건:** 후보와 기본 자원 설정을 유지할지 판단할 자료가 있다. 과부하가 있으면 `base`, partial off, 짧은 문맥, 낮은 동시 부하 등 비교할 변경과 후속 작업을 기록한다. 아직 부분 전사 스케줄러가 없는 결과로 전체 실시간 처리 가능성을 단정하지 않는다.
- **실패 시:** 후보/설정을 재비교하고 실행 가능한 조합이 없으면 모델 선택을 보류한다. 단독 실행 결과만으로 M0 모델 경로를 채택하지 않는다.
- **요구/시험:** NF-002/005/008 / 추가 probe `P0-CONTENTION`. 최종 자원 예산·게임 공존·2시간 안정성은 M5다.

## 결과 기록과 M0 종료 판정

향후 `docs/STATUS.md`에는 작업과 OS별 상태를, `benchmarks/results/<실행-ID>/`에는 기계·버전·설정·모델/fixture 해시·명령·측정값을 기록한다. 상세 시험 기록에는 관련 요구/시험 ID, 예상 결과, 관측 결과, PASS/FAIL/SKIPPED/BLOCKED, 다음 조치가 있어야 한다. 음원/전사/번역 평가 데이터는 허용된 시험 자료만 별도 보관하고 일반 진단 로그에 섞지 않는다.

M0 종료 시 다음 항목을 한 번에 확인한다.

- [ ] T00-01 통신·수명이 양 OS에서 확인됐다.
- [ ] T00-02/03 실제 캡처와 Mac 번들 권한이 통과했다.
- [ ] T00-04.1/2/4의 증거로 채택 가능한 모델·수명·자원 경로를 정했다.
- [ ] T00-04.3의 기본 창 동작과 지원 범위를 확인했다.
- [ ] 수명 오류·실행 불가 등 후속 통합을 막는 실패가 해결됐다. 성능·품질의 열린 문제에는 M1~M3 담당 작업과 재측정 기준이 연결돼 있다.

미실행 플랫폼이 있으면 M0 전체는 미통과다. 이를 이유로 독립적인 pure-core/fixture 작업까지 중단할 필요는 없다. 다음 단계에서 구현 전에 확정할 snapshot·PCM 소유권·번역 취소 상태 계약은 상위 계획의 미결정 표를 따른다.

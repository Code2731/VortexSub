# 결과에 따른 부분 전사 스케줄링

## 사용

`run-live-cuda-fast.bat`으로 실행하고 세션 시작 전에 **안정된 부분 먼저 번역 ·
임시 결과**와 **자막 지연 기록**을 켠다. 기존 기본 모드/기본 꺼짐은 유지한다.
첫 요청은 0.8초로 복구했고, 이후 빠른 모드의 재전사 시점을 결과에 따라 선택한다.

## 정책

VAD는 약 0.256초마다 현재 segment의 후보를 보낸다. worker는 이전 접수 이후
아래만큼 **새 오디오**가 쌓였을 때 실제 전사를 요청한다.

| 결과 | 다음 요청의 새 오디오 조건 |
|---|---:|
| 빈/무효/실패 결과 | 0.512초 |
| 새 원문, 안정 prefix가 아직 없거나 동일 | 0.256초 재확인 |
| 안정 prefix 증가/변화 | 0.512초 |
| 원문과 안정 prefix 모두 반복 | 0.768→최대 1.024초 |

처리 비용의 1.25배를 512-sample 프레임으로 올림한 값도 최소 간격에 반영한다
(상한 1.024초). 실행 중인 native 작업과 임시 HTTP 예약은 계속 보호하므로
상한은 실제 응답 시간 보장이 아니다. 새 입력 없는 반복 추론은 만들지 않는다.
최신 후보 하나만 보관하고 오래된 PCM은 버린다. 확정 작업은 간격을 우회하며
Pause/Stop/epoch 및 segment 전환에서 피드백을 초기화한다.

두 전사 일치와 미완성 번역 조각의 보류는 유지한다. 기존 HTTP 0.5초 요청
간격과 완료 대기는 여전히 첫 출력에 영향을 줄 수 있다. 정책은 음성 캡처
callback 밖의 processing thread에서 실행한다. 마지막 원문/안정 prefix 각각
최대 4096/1024바이트 한 쌍만 보관하며 순수 상태 판정에 모델/HTTP를 넣지 않는다.

## 확인

Windows·RTX 3080·기존 Whisper base CUDA와 Qwen3 4B Q4_K_M, 동일 7.605초
합성 영어 파일의 고정 0.512초/적응형 조건을 각각 3회 비교했다.
첫 번역 중앙값 **2.016→1.738초**, 첫 안정 원문 **1.886→1.625초**다.
누적 native decode **1.398→1.049초**, 확정 번역 **8.150→8.005초**다.
실제 HTTP를 사용하지만 VAD/캡처/화면/게임은 포함하지 않는다.
조건 순서를 번갈아 실행했으며 작은 반복 수·합성 영어 결과다. 최종 ASR 원문은
6회 같았지만 번역 표현/절 순서 차이와 품질 문제는 남아 품질 gate는 false다.

재현: `scripts/probe-paced-translation.ps1 -Backend cuda -Rounds 3 -Adaptive`.
원본과 중간 harness 보정은 [근거](evidence/adaptive-partial-windows-20261002.md)에 기록한다.
사용자 로그의 전체 음성→화면 지연과 오역/수정 빈도 확인은 별도다.

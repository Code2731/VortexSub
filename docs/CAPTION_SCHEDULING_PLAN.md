# 자막 표시 대기 구조 개선안

2026-10-10. 시뮬레이션·입력 계약·재사용 증거·후보 줄 배정기와 화면 진단을 구현했다.
선택된 기록 전달 어댑터를 진단 경로에 연결했다. 기존 golden 3개 차이 때문에 기본 전환은 보류했다.
실제 worker·음성 효과는 아직 미검증이다.
[현재 구조 판단](evidence/caption-architecture-assessment-20261008.md)과
[자동 검증](CAPTION_AUTOMATION.md)을 기준으로 한다.

## 현재 문제

`CaptionLines`의 `consumed`는 표시 이력과 현재 번역의 진행 위치를 함께 나타낸다.
교정 시 `rewrite`가 설정되면 표시 줄이 남아 있는 동안 진행이 막힌다.
`CaptionAssembly.ReusablePrefix`는 글자까지 같은 앞 문장만 재사용한다.
첫 문장이 바뀌면 뒤의 같은 문장까지 다시 표시할 수 있다.
같은 입력 식별자의 대기 수정은 이미 합친다. 그 기능을 새 구현으로 설명하지 않는다.
열린 줄 덧붙이기와 빈 아랫줄 배정도 일부 구현돼 있다.

## 입력과 상태 분리

1. 표시 이력: 표시한 원문 단위, 번역 조각, revision, 줄 배정과 읽기 기한을 보관한다.
   표시했다는 상태는 번역 의미가 확정됐다는 뜻이 아니다.
   줄이 사라져도 제한된 비교 이력을 유지한다. 세션·epoch 변경 시 초기화한다.
2. 미표시 내용: 같은 원문 단위의 최신 번역만 보관한다.
   새 revision이 들어오면 미표시 내용을 교체한다. 표시한 이력은 덮어쓰지 않는다.
3. 교정 후보: 표시한 내용과 새 번역이 달라지면 해당 단위의 교정을 보관한다.
   교정 후보도 같은 단위에서 합친다. 다른 발화의 최종 번역과 합치지 않는다.

식별자는 기존 product/session/epoch/segment/unit을 사용한다.
부분 단위와 전체 최종 번역의 원문 범위가 겹치면 겹침 관계를 명시해야 한다.
원문 범위만으로 번역 글자 위치를 추정하지 않는다.
대응 관계가 불명확하면 전체 교정으로 처리하고 그 사유를 기록한다.
이 입력 계약을 먼저 정한 뒤 표시기를 변경한다.

## 갱신 알고리즘

- 기존 표시 내용의 뒤에만 글자가 추가됐으면 미표시 꼬리를 이어 표시한다.
- 같은 단위의 번역을 완결된 문장 조각으로 비교한다.
  글자까지 같은 조각의 순서와 대응이 명확하면 재표시하지 않는다.
  앞 문장이 바뀌어도 뒤의 같은 문장을 재사용할 수 있는지 검토한다.
- 달라진 문장은 온전한 문장으로 교정한다. 서로 다른 번역의 단어를 임의로 이어 붙이지 않는다.
  같은 문장이 여러 번 나타나 대응이 모호하면 재사용하지 않는다.
- 정확한 동일성 비교만 사용한다. 동의어·숫자·부정 표현의 의미 동등성을 추측하지 않는다.
  기존 마침표 예외 범위는 유지한다. 새 의미 분류 모델은 추가하지 않는다.
- 비교 입력, 조각 수와 표시 이력은 제한한다. 상한·퇴역 규칙은 입력 계약에 포함한다.

예: 기존 번역이 `내일 출발합니다. 표는 예약했습니다.`이고 최종 번역이
`다음 주에 출발합니다. 표는 예약했습니다.`이면 첫 문장은 교정 후보다.
두 번째 문장은 같은 단위에서 대응이 명확한 경우 재표시하지 않는다.
이 예는 문자열 비교 예다. 자동 의미 판정의 성공 사례가 아니다.

## 줄 배정과 과부하

대기열에는 번역 카드 전체 대신 다음 표시 조각과 교정 작업을 둔다.
문장 전체의 전환을 기다리는 장벽을 줄 단위의 배정 조건으로 바꾼다.
읽기 기한과 발화 순서가 허용하면 빈 줄에 다음 조각을 넣는다.
보이는 줄의 위치와 최소 2.5초 읽기 보호는 유지한다.
아랫줄만 남은 경우 새 내용을 윗줄에 넣는 순서 역전은 허용하지 않는다.
교정은 관련 줄의 읽기가 끝난 뒤 처리한다. 다음 발화가 교정을 무한히 밀어내지 않게 한다.
교정과 새 발화의 순서 규칙은 trace로 검증한 뒤 확정한다.

동일 구간의 오래된 미표시 수정본은 최신 수정본으로 합친다.
서로 다른 최종 발화는 이 규칙으로 제거하지 않는다.
최종 번역 기록은 기존 기록 한도 안에서 보관한다.
오버레이가 처리하지 못한 내용은 별도 사유와 개수로 기록한다.
과부하 시 무누락·즉시 표시·읽기 보호의 동시 보장은 불가능하다.
이번 설계만으로 읽기 시간을 줄이거나 임의 요약 정책을 도입하지 않는다.

## 구현 순서와 판정

1. 제품 코드를 바꾸기 전에 같은 trace로 현재 정책과 제안 정책을 시뮬레이션한다.
   표시 이력 분리·문장 조각 LCS·줄 배정, 꼬리 합의, 끝부분 보류를 각각 비교한다.
2. 통과한 정책의 표시 이력·미표시 내용·교정 후보 계약과 제한을 구현한다.
3. 동일 단위의 조각 비교를 구현한다. 대응이 모호하거나 삭제 교정이 필요한 경우 전체 교정을 유지한다.
4. 줄 단위 배정과 과부하 기록을 연결하고 상태·렌더 회귀를 실행한다.

`scripts/test-captions.ps1`로 기존 상태·렌더·픽셀 회귀를 먼저 확인한다.
앞 문장 교정/뒤 문장 동일, 반복 문장, 부분→전체 final, 짧아진 final,
반복 revision, 숫자·부정 변경, 빠른 연속 발화와 과부하를 추가한다.
조기 삭제·줄 이동·미표시 누락·최종 교정 유실이 증가하면 실패다.
첫 줄 대기와 재표시 글자 수를 같은 입력으로 비교한다.
동일 조각의 중복 표시 감소와 불필요한 전환 대기 감소를 각각 판정한다.
기존 사용자 로그에는 자막 본문이 없으므로 그 로그만으로 교정 의미를 재생할 수 없다.
고정 입력의 성공을 실제 음성 지연이나 의미 품질의 성공으로 해석하지 않는다.
이번 설계 설명 단계에는 사용자 수동 재시험을 요청하지 않는다.

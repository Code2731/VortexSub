# T00-04.4 Windows ASR·번역 동시 부하

## 범위와 재현

2026-09-30, Windows 26200 x64 / 논리 CPU 16개 / RTX 3080 10240 MiB,
드라이버 617.14. 계획의 두 기준 장치를 대신한 현재 Windows 장치 한 대다.
Mac은 BLOCKED다. worker/UI에 캡처·모델을 연결한 시험은 아니다.
요구 NF-002/005/008, 시험 P0-CONTENTION의 독립 probe 범위를 다룬다.

```powershell

```

실제 서버는 설치된 Tabby CUDA124 배포의 llama-server build 6047
(`952a47f4`)다. Whisper는 고정된 whisper-rs 0.14.4 / sys 0.13.1,
MSVC release 최적화와 CUDA architecture 86을 사용했다. 모델 세 파일과
ASR 입력은 기존 catalogue/fixture SHA 검증을 통과했다.
전체 raw 결과·음원·출력 문장은 Git에서 제외한다. 요약 JSON에는 모델 및
fixture 식별자, 보고서·실행 바이너리 해시와 집계값을 보관한다.

## 측정 방식

- 순서: base 단독 → small 단독 → 번역 단독 → base+번역 → small+번역.
  각 조건 302초, 동시 조건은 실제 겹친 측정 구간 300초 이상을 확인한다.
  조건마다 새 프로세스/서버를 시작하며 로딩과 첫 요청 warm-up은 제외한다.
- 두 클라이언트는 공통 미래 UTC 시각에 시작하고 각자의 단조 시계로
  처리 시간을 측정한다. 마지막 요청이 구간 밖에서 완료되면 별도로 센다.
- ASR은 EN/KO 합성 발화 각 10개를 반복한다. 무음 fixture는 제외한다.
  번역은 작성된 EN/JA 문장 각 10개를 반복한다. 입력은 독립적이며
  ASR 출력이 번역 입력으로 이어지지 않는다.
- 각 엔진에 0.25초 간격으로 요청을 제공한다. 요청 하나만 실행하고
  pending queue는 0이다. 밀린 arrival은 건너뛰며 완료+실패+건너뜀을
  제공 수와 대조한다. 다음 입력을 arrival index로 선택한다.
- ASR 스레드 8개, 번역 문맥 4096토큰/parallel 1/temperature 0/
  최대 출력 256토큰을 모든 조건에서 유지한다. 반복 번역은 runtime의
  기본 prompt cache 동작에서 이득을 얻을 수 있다.
- 전사는 native decode, 번역은 로컬 HTTP 요청 시간을 측정한다.
  P50/P95는 nearest-rank다. 평균·최대·시작 지연·첫/마지막 60초·fixture별
  분포·오류·완료 수를 보존한다. 이 시간은 자막 표시 지연이 아니다.

## 후보와 후속 설정

1. **base를 M2 첫 통합의 성능 후보로 유지한다.** 이번 부하에서 요청
   건너뜀 없이 실행됐다. Qwen과 small도 실행 후보로 유지하지만,
   번역 의미 오류와 자연 음성 검증 부재로 제품 품질 채택은 보류한다.
2. **small+번역의 초당 4회 전사 설정은 여유 있는 기본값으로 채택하지
   않는다.** partial off를 먼저 연결하고, partial을 넣을 때 0.5초 간격
   이하 빈도(초당 2회)를 우선 재측정한다. 번역은 매 partial마다 실행하는
   대신 final 우선으로 낮은 부하 조합을 비교한다. 이 설정은 아직 제품에
   구현되거나 측정되지 않았다. 문맥 축소/모델 변경은 품질 영향도 함께 본다.
3. M1 유한 큐와 PCM 소유권/gap 계약, M2 partial/final 스케줄러,
   M3 final 우선·stale 결과 처리를 구현한다. probe의 입력 건너뜀을
   실제 PCM/최종 자막을 버리는 정책으로 그대로 옮기지 않는다.
4. M5에서 실제 게임, 더 작은 VRAM 장치, 긴 발화와 2시간 지속 부하를
   측정한다. 동시 부하 중 취소 응답도 재측정하며 현재 취소 deadline을
   고정하지 않는다. Mac·기준 장치 결과와 품질 gate가 열려 있어 M0 전체는
   미통과다. 독립 pure-core/fixture 구현은 계속할 수 있다.

## 검증 기록

`scripts/check.ps1`의 Rust fmt/기존 9개 시험, 양 언어 빌드, C#↔Rust
smoke가 통과했다. 먼저 5초 base 동시 harness 실행을 했고, 마지막 arrival
처리 후에도 전 시간창을 유지하도록 번역 loop를 보완한 후 본 측정을 했다.
본 측정 중 client 바이너리는 변경하지 않았다. wrapper의 atomic gate
publication과 실제 종료 시각을 반영하는 overlap 검사는 이후 보완했으며,
원래 실행에 대한 실제 종료 시각 재집계로도 두 동시 구간이 300초 이상이다.
실행 DLL/source hash와 이 차이는 요약의 `build_inputs`에 보존한다.

## 메모리와 해석 한계

약 1초 간격으로 소유 프로세스들의 working set/private bytes 합을
샘플링한다. simultaneous sum의 관측 최대이며 각 프로세스 peak의 합이
아니다. GPU 수치는 `nvidia-smi`의 **장치 전체** 사용량으로, 다른 앱이
포함된다. 프로세스별 VRAM peak나 연속 시간 utilization 평균으로 해석하지
않는다. 초기 로딩과 측정 구간 밖 샘플은 집계에서 제외한다.

대기열 증가를 막는 정책을 명시적으로 사용했으므로, 낮은 시작 지연만으로
무한 큐가 안정적이라고 판단할 수 없다. 건너뜀·arrival에서 완료까지 시간과
마지막 60초의 변화도 함께 확인한다. 입력 간격을 넘긴 응답은 이번 stress
간격과의 비교이며 제품 latency 요구 위반 판정은 아니다.

조건별 한 번의 순차 실행이다. 다른 프로세스·GPU clock·온도 영향과
실행 순서 효과를 제거한 통계적 반복 시험은 아니다. 게임을 probe에서
실행하지 않았으며 게임 공존·긴 발화·자연 음성·일본어 ASR·CPU 동시 부하·
macOS·2시간 안정성은 미검증이다. 기존 번역 의미 오류와 ASR 품질 보류도
그대로 열린 문제다.



최종 `scripts/check.ps1`도 다시 통과했다. 보완한 wrapper는
`contention-20260930-085420-ca33b1554a994e0abb88a2055fa626b7`의 5초

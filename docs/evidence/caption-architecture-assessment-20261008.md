# 자막 수정 반복과 구조 제약 검토

2026-10-08. 사용자 질문: 테스트·수정 반복으로 해결 가능한가, 아키텍처 한계인가?
현재 코드와 [실제 사용자 로그](caption-early-clear-windows-20261008.md)를 대조했다.
이번은 판단과 후속 방향 기록이다. 코드·제품 정책은 변경하지 않았다.

## 판단

수정 가능한 버그와 표시 정책의 용량 제약이 함께 있다.
원문 수정 시 읽기 기한을 우회한 조기 삭제는 버그다. 후속 수정을 구현했지만 실행 검증은 남아 있다.
줄바꿈만으로 기한을 연장하거나 빈 아랫줄을 사용하지 못한 경로도 수정 가능한 문제다.
이러한 수정의 성공을 전체 지연 해결로 해석하지 않는다.

현재 두 읽기 슬롯은 각 줄을 최소 2.5초 보호한다.
각 슬롯을 완전히 새 줄로 교체하는 평균 용량은 이상적인 조건에서도 초당 0.8줄 이하다.
이는 두 슬롯/2.5초의 용량 상한이다. 열린 줄의 글자 추가 속도나 실제 측정 처리량은 아니다.
아랫줄 보호·0.25초 간격·글자 증가·교정 대기는 실제 용량을 더 낮출 수 있다.
새 줄 유입이 이 용량보다 빠르면 대기 또는 명시적인 과부하 처리가 필요하다.
읽기 시간·완전 보존·모든 입력의 즉시 표시를 무조건 동시에 보장할 수 없다.

`CaptionLines`는 새 단위와 교정에 같은 슬롯을 사용한다.
공통 문장 prefix를 재사용할 수 없으면 교정은 전체 입력부터 다시 표시한다.
최근 로그의 교정 29건은 prefix 재사용이 없었다. 모두 불필요한 교정이라는 뜻은 아니다.
`translation_prefix`는 원문 guard다. 변경되지 않을 한국어 번역을 보장하는 계약이 아니다.
따라서 안정된 원문만 보내도 번역의 줄별 변경 문제가 자동으로 사라지지 않는다.

최근 첫 줄 대기 P95는 4.257초, 번역 처리 P95는 0.328초였다.
서로 다른 표본이다. 합산하지 않으며 이 두 수치만으로 모든 지연의 원인을 확정하지 않는다.
현재 증거는 추론 엔진 교체보다 표시 입력 계약과 배정 정책의 검토를 우선할 근거다.

## 후속 방향

1. 현재 읽기 보호 수정의 반복 원문 수정·rollback·실패/중지 회귀를 고정 입력으로 실행한다.
2. 이미 읽은/표시한 텍스트와 아직 표시하지 않은 수정 가능 텍스트의 소유권을 정리한다.
   기존 segment/unit 식별자와 두 줄 표시기를 유지하면서 입력 계약의 변경 범위를 설계한다.
   표시 이력을 일반 수정마다 재생하지 않는다. 필요한 의미 교정의 전달 정책은 명시한다.
3. 입력 속도가 읽기 용량을 넘는 경우의 처리와 기록 보존을 명시한다.
   묵시적 문장 누락을 해결로 인정하지 않는다. 읽기 시간 조절은 별도의 사용자 정책이다.
4. 같은 입력 trace로 정책 전후를 비교한다. 조기 삭제, 수정 재표시, 첫 줄 대기,
   미표시 누락과 최종 의미 교정 보존을 함께 판정한다.

테스트는 회귀와 구조 변경의 효과를 확인하는 수단이다.
서로 다른 실제 콘텐츠를 사용한 체감 비교만으로 다음 상수를 계속 바꾸지 않는다.
아키텍처 전체를 폐기해야 한다는 근거는 없다. 표시 계층의 입력 계약과 정책 정리가 우선이다.
후속 설계는 아직 구현·실측하지 않았다. 품질·지연의 성공을 보장한 계획이 아니다.

## 상태

브랜치 `master`, 기준 HEAD `15f1db0`. 문서는 미커밋이다. 푸시·다른 PC 전달은 하지 않았다.
새 실행·빌드·자동 테스트·다운로드는 이번에 수행하지 않았다.
이전 수정의 확인 범위는 [읽기 보호 구현 근거](caption-source-reading-protection-windows-20261008.md)를 따른다.

# 읽기 줄 배정의 불필요한 대기 수정

날짜: 2026-10-08. Windows 작업 트리. 브랜치 `master`, 기준 HEAD `15f1db0`.
이번 변경은 미커밋이며 다른 PC에 전달되지 않았다.

## 근거와 변경

[직전 사용자 로그](live-delay-breakdown-windows-20261008.md)의 번역 처리 P95는 0.219초,
첫 줄 배정 대기 P95는 4.268초였다. 표본이 달라 합산하지 않는다.
로그에는 본문이 없다. 아래 재현이 실제 긴 대기 전체의 원인이라고 단정하지 않는다.

`CaptionLines`의 두 경로를 수정했다.

1. 열린 줄에 CR/LF만 추가되면 본문은 그대로인데 읽기 기한이 연장됐다.
   이제 분리자를 소비하되 기한을 유지한다. `SeparatorConsumed/ReadingDeadlineRetained`를 기록한다.
   보이는 글자가 추가되면 기존처럼 2.5초 읽기 시간을 보장한다.
2. 빈 번역 카드로 이전 입력이 취소되면 표시 줄은 남는다.
   이때 새 단위가 빈 아랫줄도 사용하지 못하고 기다렸다.
   이제 새 단위를 대기열에 넣고 순서대로 배정한다.
   윗줄만 남으면 아랫줄을 사용한다. 아랫줄이 남으면 기다린다.

줄 위치, 읽기 시간 2.5초, 두 줄 만료 간격 0.25초, 대기열 상한은 유지했다.
같은 단위의 의미 수정과 명시적 원문 철회는 기존 정책을 따른다.

## 재현과 검증

실제 표시기에 가상 시계와 합성 문자열을 입력했다.

| 재현 | 수정 전 대기 | 수정 후 대기 |
| --- | ---: | ---: |
| 두 줄 표시 후 2초에 분리자 추가; 다음 단위는 0.1초에 수신 | 4.40초 | 2.65초 |
| 윗줄 표시 후 입력 취소; 다음 단위는 0.2초에 수신 | 2.30초 | 0초 |

수정 전 재현 검사 실패와 수정 후 통과를 확인했다.
CR/LF/CRLF, 실제 글자 증가의 읽기 시간, 줄별 식별자, 대기열 순서와 누락 없음을 검사했다.
수치는 논리적 배정 시간이다. 음성부터 물리 화면까지의 실측값이 아니다.

기존 pipeline 검사 하나가 2026-10-05 원문 철회 정책과 어긋났다.
검사를 갱신해 명시적 철회 후 즉시 교정하고 만료 뒤 재표시하지 않음을 확인했다.

저장소 루트에서 기존 .NET SDK와 복원된 패키지로 실행했다. 다운로드는 없었다.

```powershell
$env:NUGET_PACKAGES = Join-Path $PWD '.nuget/packages'
$env:AVALONIA_TELEMETRY_OPTOUT = '1'
dotnet run --project tests/EchoSub.ProtocolSmoke --no-restore -- --lines-only
dotnet build apps/EchoSub.Desktop/EchoSub.Desktop.csproj --no-restore
```

- 줄 상태 99개, pipeline 46개, 전달 44개: 모두 통과. 종료 코드 0.
- 앱 빌드: 경고 0 / 오류 0. 종료 코드 0.
- 실제 음성·모델 추론·물리 화면·30분 사용·macOS·전체 Rust/IPC 검사는 이번에 미실행.
- CPU/GPU 성능 비교는 수행하지 않았다. 새 모델·런타임은 필요하지 않다.
